# Spec: bank-reconciliation (afletteren: banktransacties koppelen aan facturen)

## 1. Goal and context
Turn imported bank transactions (`bank_transaction`, status `nieuw`) into bookings. For each transaction the owner either (a) links it to one or more open inkoopfacturen / openstaande posten of the beginbalans (pay or part-pay them), (b) books it directly to a grootboekrekening without invoice (bankkosten, privé, rente, ...), or (c) ignores it. The system suggests matches (IBAN, amount, invoice number in description) and remembers choices as matching rules.

Builds on: bank import (`BankTransaction`, `BankAccount.account_id/journal_id`), purchase (`PurchaseInvoice`, `open_amount`, `invoice_status`, `paid_cents`), opening (`OpeningItem.paid_cents`, crediteur side), ledger (`post_entry`, `reverse_entry`, `NewEntry/NewLine`, locked periods), relations (`Contact.iban`, name matching), vat (`VatCode`), glossary, `Account.default_vat_code`.

Posting: every reconciliation is one balanced entry in the bank's own dagboek (`bank_account.journal_id`), `booking_date` = transaction `booking_date`, `reference` = invoice number(s) or bank reference. Money in integer cents.
- Pay invoice (transaction af): debit `3000 Crediteuren`, credit bank account. Creditnota matched (transaction bij, i.e. refund): debit bank, credit `3000`.
- Direct-book af: debit chosen account(s) (+ debit `1400` voorbelasting per btw-code, same way as `purchase.build_entry`), credit bank. Direct-book bij: debit bank, credit chosen account(s).

## 2. Non-goals
- Verkoopfacturen/debiteuren (later item). Design only: see 4.1 `OpenItem` + provider list so debiteur sources plug in without changing the UI/booking code.
- Auto-booking without user confirmation, voorschotten/on-account payments (unallocated remainder), foreign currency, bank-feed/PSD2, editing a booked match (undo + redo instead).
- Direct-book of a "bij" with btw (omzet): only btw-code without BTW (0%/geen) accepted for incoming money; omzet with BTW comes with verkoopfacturen.

## 3. User stories and acceptance criteria
Stories: As owner I want (1) to see which transactions still need booking with a suggested invoice, (2) to confirm a suggestion in one click, (3) to pay several invoices or part of an invoice with one transaction, (4) to book a bankkosten-line without invoice and have the next one suggested, (5) to undo a wrong match.

Acceptance criteria:
1. Screen `/bank/afletteren` lists transactions with status `nieuw` (filter by bankrekening, text, "af/bij"), newest first, paginated; each row shows date, tegenpartij, omschrijving, amount, and the best suggestion (invoice or rule) with a confidence label ("Zeker" / "Waarschijnlijk") and an "Akkoord" button. Nav/bank index shows the count "N te verwerken".
2. Suggestion signals (pure function, deterministic): contact IBAN equals transaction `counterparty_iban` (normalised); open amount equals transaction amount; invoice number (normalised: lowercase, alphanumerics only, min 3 chars) occurs in normalised description; contact name matches counterparty name (reuse `relations.matching`). "Zeker" = exactly one candidate set with exact amount AND (invoice number in description OR IBAN match). Anything else with at least one signal = "Waarschijnlijk". Direction must fit: transaction af suggests invoices, bij suggests creditnota's. A description naming several invoices of one contact whose open amounts sum to the transaction amount yields one multi-invoice suggestion.
3. "Akkoord" on a suggestion books it immediately (single transaction, atomic): entry posted, `bank_match` rows written, `paid_cents` of each target increased, transaction `status='geboekt'` with `journal_entry_id`. A suggestion is only offered when its allocation covers the full transaction amount.
4. Manual match page `/bank/transacties/{id}/afletteren`: tab "Past bij factuur" lists all open items (crediteur side) of the chosen leverancier (default: the matched contact, else a search field over all leveranciers) with checkbox and an amount field prefilled with the open amount (capped by remaining transaction amount). Live-ish summary: "Verdeeld €X van €Y, nog €Z te verdelen". Booking is blocked until remainder is exactly 0.
5. Partial payment: allocation < open amount is allowed; invoice stays `open` with reduced open amount (via existing `open_amount`), becomes `betaald` when `paid_cents` = total. Allocation > open amount is refused: "Je kunt maximaal €X aan deze factuur toewijzen; er staat nog €X open."
6. Split: one transaction over several invoices (also mixed with creditnota's of the same leverancier, net must equal the transaction) in one entry; one `3000` line per allocation.
7. Opening items (beginbalans crediteur posten) are matchable exactly like invoices (`OpeningItem.paid_cents`).
8. Direct-book tab "Direct boeken": one or more lines (rekening, btw-code, bedrag incl. btw, omschrijving) whose total equals the transaction amount; default rekening/btw from a matching rule, else from the last booking for the same IBAN (`last used`), else empty. Btw-code defaults from `Account.default_vat_code`. Unsupported btw codes (verlegd/EU/export) are refused with a plain message (same set as purchase). A transaction can combine invoice allocations and direct lines (e.g. bankkosten) as long as the total is exact.
9. Checkbox "Onthoud dit voor volgende keer" on direct-book creates a matching rule (see 4.3). Rules are applied only as suggestions (confidence "Waarschijnlijk", or "Zeker" when the rule matches on IBAN + description); never auto-booked. Screen `/bank/regels` lists rules (naam, wanneer, boek op rekening, btw, keer gebruikt) with deactivate/reactivate. No delete (a rule used for a booking stays traceable).
10. "Negeren" sets status `genegeerd` (with confirm text: "Deze mutatie komt niet in je boekhouding. Alleen doen als het echt niet hoort, bijvoorbeeld een dubbele regel."). "Terugzetten" sets it back to `nieuw`. Ignored transactions show in a filter "Genegeerd".
11. Undo ("Ongedaan maken") on a `geboekt` transaction: stornoboeking via `reverse_entry`, `bank_match.reversed_at` set, `paid_cents` decreased again, transaction back to `nieuw` with `journal_entry_id` NULL. Refused with plain message when the period is locked (existing `LedgerError`) or the entry is already reversed.
12. Bookings are append-only: no update/delete of entries; `bank_match` rows are never deleted (only `reversed_at` set once).
13. Errors are plain Dutch (examples): "Er is nog €12,10 niet verdeeld." / "Deze mutatie is al verwerkt." / "Een bedrag af kun je alleen koppelen aan inkoopfacturen; kies een creditnota alleen bij een bedrag dat bij komt." / "Kies een rekening voor deze regel." Never raw exceptions.
14. Concurrency/idempotency: booking the same transaction twice (double click, two tabs) yields exactly one entry; second call fails with "Deze mutatie is al verwerkt." (re-check status inside the DB transaction, same `_open_transaction` pattern as `purchase.service`).
15. Invoice list `/inkoop` and crediteuren overview reflect payments automatically (open amount / status `betaald`) with no change to their code; the invoice detail/row links to its paying transaction(s) only if cheap (optional).

Usable-without-bookkeeping (CLAUDE.md), screens lead with plain Dutch: "Welke factuur is dit?", "Wat is dit voor uitgave?", "Nog te verdelen". Glossary entries to add in `app/domain/glossary.py` (only if missing), each shown with info icon: `afletteren` (Mutatie koppelen aan factuur), `openstaande_post` (Nog niet betaalde factuur), `deelbetaling` (Gedeeltelijk betaald), `direct_boeken` (Boeken zonder factuur), `matchingregel` (Onthouden keuze voor terugkerende mutaties), `stornoboeking` (check existing `storno` term, reuse), `crediteuren`/`dagboek` already exist. Suggested defaults: contact, rekening, btw-code, amount per allocation as in 2/4/8.

## 4. Technical approach
Business logic in new package `app/domain/reconcile/`; web only parses forms and renders.

### 4.1 Domain (pure parts first, tests first)
- `types.py`: frozen dataclasses `OpenItem(source: 'purchase_invoice'|'opening_item', source_id, contact_id, contact_name, iban, number, date, due_date, open_cents (>0 for invoice, creditnota flagged by `is_credit`), side: 'crediteur')`; `Allocation(source, source_id, amount_cents)` (>0); `DirectLine(account_id, amount_cents (>0), vat_code, description)`; `Suggestion(kind: 'match'|'rule', allocations, rule_id, direct_lines, confidence: 'zeker'|'waarschijnlijk', reasons: tuple[str,...], contact_id)`.
- `matching.py` (pure, no DB): `normalize_text(s)`, `suggest(txn: TxnView, items: Sequence[OpenItem], rules: Sequence[RuleView]) -> list[Suggestion]` per AC 2; subset-sum for multi-invoice limited to <= 6 candidate invoices of one contact.
- `rules.py`: `rule_matches(rule, txn)` (IBAN equal and/or description contains normalised needle, direction), `create_rule(...)`, `set_rule_active(...)`, `list_rules(...)`. Specificity order: IBAN+needle > IBAN > needle; ties by `use_count`.
- `entries.py` (pure): `build_payment_entry(txn, bank_ledger_account_id, journal_id, allocations_with_kind, direct_lines, vat_accounts) -> NewEntry`, validates sum = |transaction amount|, validates via `validate_entry`.
- `service.py` (DB): `list_open_items(session, side='crediteur', contact_id=None, q=None) -> list[OpenItem]` (purchase invoices not storno'd with open <> 0, plus `opening_item` crediteur open, same filter as `purchase.open_by_supplier`; module keeps a `PROVIDERS` list so a sales provider can be appended later); `suggestions_for(session, txn_id)`; `list_to_process(session, *, bank_account_id, q, direction, status, page)`; `book(session, txn_id, allocations, direct_lines, *, remember_rule: RuleDraft | None) -> JournalEntry`; `accept(session, txn_id, suggestion_key)` (recomputes the suggestion server-side, never trusts posted amounts); `undo(session, txn_id) -> JournalEntry`; `ignore(session, txn_id)`, `restore(session, txn_id)`; `to_process_count(session)`.
- Errors: reuse `LedgerError` subclasses with plain Dutch messages (e.g. `ReconcileError(LedgerError)` with code + message).
- Transaction handling: check status `nieuw` inside the DB transaction, lock via the existing `_open_transaction` trick, post entry with `post_entry` (period lock / balance checks come free), then insert matches, update paid_cents (`PurchaseInvoice.paid_cents` / `OpeningItem.paid_cents`), set txn status and `journal_entry_id`. Recompute `paid_cents` as sum of non-reversed `bank_match` amounts for the item on undo (do not just subtract).

### 4.2 Data model (migration `0011_bank_reconciliation.py`, must not import app.models; models in `app/models/reconcile.py`, imported in `app/models/__init__.py`)
- `bank_match`: `id`, `bank_transaction_id` FK, `journal_entry_id` FK, `source` CHECK in ('purchase_invoice','opening_item'), `source_id` int, `amount_cents` CHECK > 0, `created_at`, `reversed_at` nullable. Index on (source, source_id) and bank_transaction_id. Triggers: no DELETE; UPDATE only of `reversed_at` from NULL to non-NULL.
- `bank_rule`: `id`, `name`, `counterparty_iban` null, `description_contains` null, `direction` CHECK in ('af','bij','beide'), `account_id` FK, `vat_code` FK null, `contact_id` FK null, `is_active` default 1, `use_count` default 0, `created_at`. CHECK at least one of iban/description_contains NOT NULL. No delete trigger needed (no delete path).
- `bank_transaction`: existing trigger allows only `status`/`journal_entry_id` changes; builder must verify it permits setting `journal_entry_id` back to NULL on undo and `genegeerd -> nieuw`, and amend the trigger in this migration if not (keep downgrade symmetrical). Check `purchase_invoice`/`opening_item` allow `paid_cents` updates (opening: yes by 0010).
- No new columns on transactions; whether a transaction was direct-booked = `geboekt` with no non-reversed `bank_match` rows.

### 4.3 Web
New `app/web/reconcile_routes.py` (register in `app/web/routes.py`), templates under `app/web/templates/bank/` (`reconcile_list.html`, `reconcile_detail.html`, `rules.html`, partials for HTMX swap of the summary/row). Routes: `GET /bank/afletteren`, `GET/POST /bank/transacties/{id}/afletteren`, `POST /bank/transacties/{id}/akkoord`, `POST .../negeren`, `.../terugzetten`, `.../ongedaan-maken`, `GET /bank/regels`, `POST /bank/regels/{id}/actief`. POST forms use post/redirect/get and re-render with plain error + 4xx (status mapping like `bank_routes._status_for`). Add link "Afletteren" on `/bank` and in `_transactions.html` rows with status `nieuw`; status chips for `geboekt`/`genegeerd`.

## 7. Risks and decisions made
- Remainder not allocated is refused (no voorschot/on-account): keeps crediteuren clean; documented non-goal. Recommended default; user can lift later.
- Suggestions only, never auto-book: bookkeeping integrity over speed; "Zeker" rows get a one-click Akkoord.
- Allocation stored in `bank_match` rather than adding transaction columns: supports split, partial, undo and future sales sources (`source` check extended by a later migration).
- Undo via storno + status reset, keeps ledger append-only while allowing the transaction to be re-processed.
- Incoming money with btw (omzet) deferred to verkoopfacturen to avoid inventing `1500` BTW-afdracht logic here.
- Same-IBAN history default for direct-book is a simple query on previous non-reversed direct-booked entries; no new table.
